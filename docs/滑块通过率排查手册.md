# 滑块通过率排查手册

> 记录于 2026-07-26。用于新开会话时快速接手排查，不必从零复现。
> 环境：Windows 云电脑（远程工具 GameViewer/ELINK 挂虚拟显示器）、pm2 托管、Git Bash + PowerShell + `.venv`。

---

## 1. 系统是怎么跑的

滑块默认走 `chrome_cdp` 模式（见 [`slider_mode.py`](../common/services/captcha/slider_mode.py)）：
CDP 连接本机 Edge（真机指纹/登录态）→ **物理鼠标**（`SendInput`）回放真人录制轨迹。

关键链路：

```
cookie_token_manager.handle_captcha_verification
  └─ orchestrator.run_slider_verification_with_fallback
       └─ real_mouse_slider.run_real_mouse_verification      ← 引擎入口、显示器前置检查
            ├─ chrome_cdp.ensure_cdp_chrome(force_clean=True) ← 拉起/复用带调试端口的 Edge
            ├─ _RealMouseSolver.prepare_task                  ← 验证标签、注入 Cookie
            └─ _RealMouseSolver.solve
                 ├─ _choose_drag / _take_drag                 ← 选轨迹（按实测通过率加权）
                 ├─ _scale_drag_to_distance                   ← X 映射 + 硬件节拍重采样
                 └─ _do_real_slide                            ← 物理鼠标回放
```

| 文件 | 职责 |
|---|---|
| [`real_mouse_slider.py`](../common/services/captcha/real_mouse_slider.py) | 引擎主体、轨迹选择/加工、CDP 页管理 |
| [`chrome_cdp.py`](../common/services/captcha/chrome_cdp.py) | Edge 拉起/探测/清理、CDP 端点 |
| [`win_input.py`](../common/services/captcha/win_input.py) | `SendInput` 原语、高精度定时、**`display_state()` 显示器检测** |
| [`real_mouse_coordinates.py`](../common/services/captcha/real_mouse_coordinates.py) | 坐标映射（`calibrate_slider_center` 目前**已无调用方**，是死代码） |
| [`trail_stats.py`](../common/services/captcha/trail_stats.py) | 每条轨迹样本的在线通过率统计 |
| [`profile_pool.py`](../common/services/captcha/profile_pool.py) | 浏览器资料池（失败后轮换 p0~p3） |
| `common/services/captcha/human_trails/*.json` | 真人录制轨迹样本 |
| `run/captcha_trail_stats.json` | 样本通过率持久化（**运行时文件，被服务实时改写**） |

判定成功的信号：`x5sec` cookie 更新。`code=300` = 风控明确拒绝（滑动发生了但被判假）。
> 注意：实测从未出现过 `code=0`，成功一律靠 x5sec 变化识别，不要误以为 code=0 缺失是 bug。

## 2. 已确认的根因：远程断开 → 分辨率降级

**这是目前最强的单一因素，排查任何通过率问题都要先排除它。**

| 虚拟桌面 | 任务数 | 通过 | 拒绝 | 通过率 | 场景 |
|---|---|---|---|---|---|
| `1@1616x996` | 8 | 9 | 0 | **100%** | 远程连接中（装 Parsec 前） |
| `2@3536x1080` | 3 | 3 | 0 | **100%** | 远程连接中（装 Parsec 后，双屏） |
| `2@2944x1080` | 4 | 4 | 0 | **100%** | **远程断开 + Parsec 顶住** |
| `1@1024x768` | 2 | 0 | 8 | **0%** | 远程断开（装 Parsec 前） |

n=24，相关性无一例外。**分辨率是目前对通过率影响最大的单一变量——比轨迹样本、比映射方式的影响都大得多。**
排查任何通过率问题，第一件事就是跑 §3.1 排除它。

机制：显示器由远程工具虚拟挂载。断开后显示器**不消失、而是掉到 1024x768**（Windows 无头会话回退分辨率），于是

1. `SendInput` 绝对坐标按虚拟桌面尺寸归一化（[`win_input.py`](../common/services/captcha/win_input.py) 的 `send_move_abs`），基准变了 → 落点偏移
2. 浏览器窗口被重排 → 滑轨几何与样本录制时对不上
3. Chromium 降级合成 + 节流定时器 → 7.6ms 回放节拍被打散

**现有防护**：`run_real_mouse_verification` 开头调 `display_state()`，检测到 `≤1024x768` 就直接跳过、不硬滑，避免白送 `code=300`（会抬 `_risk_level` 并污染 `trail_stats`）。
阈值可用 `CAPTCHA_MIN_SCREEN_W` / `CAPTCHA_MIN_SCREEN_H` 覆盖。

### 2.1 已根治：装 Parsec Virtual Display Driver（2026-07-26 22:06 验证通过）

装了 **parsec-vdd** 并添加一块虚拟屏后，断开远程时的行为变成：

```
断开前: 2 屏 3536x1080 | ELINK DISPLAY WDDM DRIVER + Parsec Virtual Display Adapter
断开后: 2 屏 2944x1080 | Microsoft Basic Display Adapter + Parsec Virtual Display Adapter
        DISPLAY62 (Parsec 1920x1080) @ (0,0)    Primary=True   ← 自动接管主屏
        DISPLAY89 (Basic  1024x768)  @ (1920,0) Primary=False
        Edge 窗口 (-8,-8)-(1928,1040)                          ← 留在 Parsec 屏上
```

**断开状态下滑块正常通过。** 关键是 Parsec **抢到了主屏**，Edge 没被赶到那块 1024x768 的降级屏；
`send_move_abs` 的归一化基准（实时读的 2944x1080）与窗口几何自洽，坐标不偏。

> ⚠️ 注意 `display_state()` 现在看的是**虚拟桌面总尺寸**（2944x1080 → usable=True）。
> 那块 1024x768 的降级屏其实还在，只是变成了副屏。
> **如果哪天 Parsec 没抢到主屏、Edge 落到降级屏上，总尺寸检查是拦不住的**——
> 届时症状是「有显示器、usable=True，但仍稳定 code=300」。
> 真出现这种情况，判定标准要改成「Edge 主窗口所在的那块屏的分辨率」，
> 用 §3.7 下面那段 PowerShell 查窗口落在哪块屏上。

### 2.2 ⚠ 未解决：Parsec 虚拟屏在**重连后会被摘掉**

实测三阶段（2026-07-26）：

| 时刻 | 桌面显示器 | 状态 |
|---|---|---|
| 22:03 连接中 | ELINK 1616x996 + **Parsec 1920x1080**（3536x1080） | 手动添加后 |
| 22:06 断开 | Basic 1024x768 + **Parsec 1920x1080**（2944x1080） | ✅ 顶住，8/8 通过 |
| 22:46 **重连** | **仅 ELINK 1616x996** | ❌ **Parsec 已不在显示器列表** |

Parsec 的适配器还在（`Get-CimInstance Win32_VideoController` 能看到 1920x1080），
但已不再 attach 到桌面。**也就是说重连一次，断开保护就没了**——
此时再断开，很可能退回 `1024x768` 的坏状态。

**断开前必须自查**（列表里除 ELINK 外还有 ≥1280x720 的屏才安全）：

```powershell
Add-Type -AssemblyName System.Windows.Forms
[System.Windows.Forms.Screen]::AllScreens | ForEach-Object { "$($_.DeviceName) $($_.Bounds) Primary=$($_.Primary)" }
```

**待办**：让虚拟屏常驻、不随远程会话增删。方向——
Parsec VDD 的持久化配置；或改用以「常驻」为设计目标的 `usbmmidd_v2`（Amyuni）；
或 GameViewer 自带的「断开后保持虚拟显示器」选项（未验证）。

### 2.3 ⚠ 看数据前先分清两个口径（很容易误判）

同一批日志，两种算法会得出完全相反的结论：

| 口径 | 含义 | 怎么算 |
|---|---|---|
| **任务级** | 这个账号最终有没有拿到 token | 一个「启动滑块引擎」到下一个之间，出现过 `x5sec 更新` 就算成功 |
| **单次滑动** | 每一次物理回放有没有被判过 | 数 `x5sec 更新` : `code=300` 的比例 |

实测 `2@3584x1440` 布局下：**任务级 21/21 = 100%，单次滑动只有 38.9%，平均每任务滑 2.6 次**。
即「每次都要多滑 2~3 次才过」，不是「失败」。

- 报「系统坏了」之前先看任务级（§3.9）——**任务级掉了才是真出事**
- 单次滑动率反映的是**代价**：更慢、更容易触发 `_risk_level` 升级、风控侧留下更多失败记录
- §3.2 的脚本算的是**单次滑动**口径，别拿它当系统健康度

### 2.4 ⚠ 样本适配性会「跟着显示配置变」

同一批样本在不同显示布局下表现差异极大。`2@3584x1440` 下实测：

| 样本 | 该布局下 | 而在 `1616x996` 下 |
|---|---|---|
| `1783949657` | 6/7 = 85.7% | — |
| `1783949718` | 4/7 = 57.1% | — |
| `1783949589` | 3/6 = 50.0% | **74%（曾是第一名）** |
| `1784203585` | 2/7 = 28.6% | **70%（曾是第二名）** |
| `1784018353` | **0/8** | 39% |
| `1783949622` | **0/4** | — |
| `1783943859` | **0/3** | — |

推测原因：滑轨渲染宽度随浏览器窗口（即分辨率）变化，样本经 `_scale_drag_to_distance`
缩放后速度曲线的绝对尺度也跟着变，与录制时的匹配度就不同了。**未验证，仅为假设。**

**含义**：`trail_stats` 目前是**全局** key（只按文件名），显示配置一变统计就被稀释。
若长期在多种分辨率间切换，正解是把显示配置并入统计 key（如 `样本名@1616x996`），
让引擎按分辨率分别学习；若能固定一种分辨率则不必改。

## 3. 排查手段（可直接复制运行）

所有命令在项目根目录、Git Bash 下运行。日志主文件：`logs/pm2/websocket-err.log`（滑块引擎跑在 websocket 进程里；scheduler/backend-web 的日志里没有）。

### 3.1 最重要的一条：显示器状态 vs 结果

**任何通过率异常先跑这个**，能立刻排除环境因素。启动日志里带 `显示器=N@WxH`。

```bash
cd "c:/Users/Admin/Projects/xianyu-auto-reply" && ./.venv/Scripts/python.exe - <<'PYEOF' 2>/dev/null
import re, collections
start=re.compile(r"【([^】]+)】启动滑块引擎.*显示器=(\d+)@(\d+)x(\d+)")
recs=[]; cur=None
for line in open("logs/pm2/websocket-err.log", encoding="utf-8", errors="ignore"):
    m=start.search(line)
    if m:
        if cur: recs.append(cur)
        cur={"t":line[:19],"mon":m.group(2),"res":f"{m.group(3)}x{m.group(4)}","ok":0,"bad":0}
        continue
    if cur is None: continue
    if "滑块接口返回 code=300" in line: cur["bad"]+=1
    elif "检测到 x5sec 更新" in line or "滑块接口返回 code=0" in line: cur["ok"]+=1
if cur: recs.append(cur)
g=collections.defaultdict(lambda:[0,0])
for r in recs:
    k=r['mon']+'@'+r['res']; g[k][0]+=r['ok']; g[k][1]+=r['bad']
print("按分辨率汇总:")
for k,(o,b) in g.items():
    n=o+b
    print(f"  {k:14} 通过={o:3} 拒绝={b:3}  通过率={100*o/n if n else 0:5.1f}%")
PYEOF
```

```bash

g=collections.defaultdict(collections.Counter)
for k,o in recs: g[k][o]+=1
for k,c in sorted(g.items(), key=lambda kv:-sum(kv[1].values())):
```

**查 Edge 窗口落在哪块屏上**（多屏时排查坐标偏移的关键，见 §2.1 的警告）：

```powershell
Add-Type -AssemblyName System.Windows.Forms

[System.Windows.Forms.Screen]::AllScreens | ForEach-Object { "  $($_.DeviceName) $($_.Bounds) Primary=$($_.Primary)" }
Add-Type -Name W -Namespace N2 -MemberDefinition @'
[DllImport("user32.dll")] public static extern bool GetWindowRect(IntPtr h, out RECT r);
public struct RECT { public int L, T, R, B; }
'@
"Edge 主窗口:"
Get-Process msedge -ErrorAction SilentlyContinue | Where-Object { $_.MainWindowHandle -ne 0 } | ForEach-Object {
  $r = New-Object N2.W+RECT
  [void][N2.W]::GetWindowRect($_.MainWindowHandle, [ref]$r)
  "  PID=$($_.Id) ($($r.L),$($r.T))-($($r.R),$($r.B)) 宽=$($r.R-$r.L) 高=$($r.B-$r.T)"
}
```

### 3.8 日志小技巧

- 日志带 ANSI 颜色码，`grep` 前先 `sed 's/\x1b\[[0-9;]*m//g'`
- 中文在 Git Bash 里可能显示为乱码，但 `grep` 匹配是好的；要看清内容用 `./.venv/Scripts/python.exe` 读
- 按时间切片：`awk '$0 >= "2026-07-26T18:46" && $0 <= "2026-07-26T18:48"' logs/pm2/websocket-err.log`
- `grep -c` 无匹配时会输出 `0` 且退出码为 1，在 `$(...)` 里要写 `n=${n:-0}` 兜底，否则 shell 算术会报错

### 3.9 任务级通过率（区别于 §3.2 的单次滑动口径）

```bash
cd "c:/Users/Admin/Projects/xianyu-auto-reply" && ./.venv/Scripts/python.exe - <<'PYEOF' 2>/dev/null

SINCE = "2026-07-26T22:46"        # ← 改成你要统计的起始时间
```

## 4. 已修复的坑（附判据，避免重复踩）

### 4.1 pm2 继承 `http_proxy` 但无 `no_proxy` → CDP 探测永远失败

**症状**：日志刷「Edge 已拉起但 CDP 端口 9222 未在超时内就绪」，浏览器窗口一闪就没了。

**根因**：`pm2 env 1` 显示服务继承了 `http_proxy=http://127.0.0.1:10808` 却没有 `no_proxy`。
CPython 的 `urllib` 一旦在环境变量里发现代理，`proxy_bypass()` 就只查 `no_proxy`、**不再读注册表的 `ProxyOverride`**（那里本来有 `127.*`），于是 `urlopen("http://127.0.0.1:9222/...")` 被发给代理并返回 **HTTP 503**。

**判据**（同一时刻对比）：
```bash
curl -s -o /dev/null -w "外部 %{http_code}\n" --noproxy '*' http://127.0.0.1:9222/json/version
http_proxy=http://127.0.0.1:10808 ./.venv/Scripts/python.exe -c "
import urllib.request
try: urllib.request.urlopen('http://127.0.0.1:9222/json/version',timeout=1.5); print('旧写法 OK')
except Exception as e: print('旧写法', type(e).__name__, e)
import sys; sys.path.insert(0,'.')
from common.services.captcha.chrome_cdp import is_cdp_ready
print('新写法 is_cdp_ready:', is_cdp_ready())
"
```

**修**：`is_cdp_ready()` 改用 `build_opener(ProxyHandler({}))` 强制直连；`ecosystem.config.cjs` 的 app env 加了 `NO_PROXY`/`no_proxy` 回环白名单。
> `pm2 restart` **不会**刷新 env，改了要 `pm2 start ecosystem.config.cjs --update-env`。

### 4.2 `kill_cdp_chrome()` 不等进程退出 → 新 Edge 被单实例机制吞掉

**症状**：同上，浏览器窗口一闪即逝。

**根因**：`taskkill` 返回时仍有 13 个 msedge 存活，`user-data-dir` 的 lockfile 没释放；新 Edge 发现已有实例，转交命令行后自己退出，调试端口没人绑定。

**修**：kill 后轮询 `count_cdp_browser_processes()` 直到归零（上限 6s）；`launch_chrome_with_cdp` 改成 15s×2 带清理重试，不再空等 52s。

### 4.3 pm2 里的 `browser-cdp` 守护进程与 Python 抢浏览器

**已从 `ecosystem.config.cjs` 移除，脚本已删，别再加回来**（配置里有注释说明原因）。
它每 8s 轮询拉起 Edge，会和 `ensure_cdp_chrome(force_clean=True)` 撞在同一个 `user-data-dir` 上。

### 4.4 `_choose_drag` 静态打分把最好的样本压到最低权重

**根因**：旧实现按「点数 + 时长」打分，时长 <800ms 的样本权重 0.05——而真人录制样本正好都是 424~432ms。
结果：合成兜底轨迹（通过率 7.1%）拿走了 **95.7%** 的回放机会。

**修**：改为按 `trail_stats` 实测通过率加权（Laplace 平滑 + 采样不足探索加成），合成轨迹额外 ×0.12。
**不要改回任何形式的「短样本降权」。**

### 4.5 回放事件密度只有 ~30Hz

真人硬件鼠标相邻 `mousemove` 间隔中位数 6.7~8.0ms（125~150Hz）。旧实现把时间轴拉长到 1100~2500ms 却不加点，密度掉到 30Hz 量级，是合成输入的显著特征。
**修**：`_resample_to_hardware_cadence` 按累计时间轴线性插值补点到 ~7.6ms/点。

### 4.6 其他已删的浪费

- `_inject_account_cookies` 里的 `goto("goofish.com/favicon.ico")`——`add_cookies` 带显式 domain 时根本不需要导航，慢网下卡满 8s
- `activate_window` / `_ensure_window_foreground` 不检查窗口是否已在前台就执行整套强制置顶（一次任务调 6~9 次）→ 这是「浏览器反复闪烁」的来源，已加快路径

## 5. 未决事项

### 5.1 `trail_stats` 有脏数据

`run/captcha_trail_stats.json` 里 4 条上游样本（`1783943859` / `1783949622` / `1783949657` / `1783949718`）的 8~13% 是**远程断开期间测出来的**，被环境冤枉了。

建议停服务后清零重测：
```bash
pm2 stop websocket
rm run/captcha_trail_stats.json
pm2 start websocket
```
> 该文件被服务实时改写，**不要在服务运行时编辑**。它也不该入库（见 §5.3）。

### 5.2 X 映射方式的 A/B 没做

两种映射，目前用的是前者：

| 方式 | 说明 | 现状 |
|---|---|---|
| **末点归一**（当前） | `factor = distance / 样本末点`，末点精确贴合终点，不回放超出段 | 1616x996 下 3/3 |
| **采集基准 + 保留超出段**（上游 `bda1a85`） | `factor = distance / capture_distance`，回放真人到底后的超出段；配 `_MAX_BUSINESS_CAPTURE_OVERSHOOT_PX=80` 剔长尾样本 | 只在断开期间测过，数据不可用 |

**当初判定上游方式差是错的**（被 §2 的显示器问题混淆）。等环境稳定后要重做干净对比。
切换点：[`real_mouse_slider.py`](../common/services/captcha/real_mouse_slider.py) 的 `_scale_drag_to_distance` + 常量 `_MAX_BUSINESS_CAPTURE_OVERSHOOT_PX`（置 0 = 不按超出段筛样本）。

### 5.3 `run/` 下的运行时文件被提交进了仓库

`run/captcha_profile_index.txt`、`run/captcha_profile_path.txt`、`run/captcha_trail_stats.json` 是服务自己写的状态，不该跟踪。
副作用：`git status` 长期是脏的，**rebase/merge 时会因工作区不干净而失败**，且 git 报错信息具有误导性（会说 "You must edit all merge conflicts"）。

```bash
git rm --cached run/captcha_profile_index.txt run/captcha_profile_path.txt run/captcha_trail_stats.json
echo "run/" >> .gitignore
```

### 5.4 资料池首次失败就轮换，代价大

`run_real_mouse_verification` 现在**首次失败就换浏览器资料**，而轮换目标是资料池里一个全新空目录 → 杀 Edge、无缓存无 cookie 冷启动，页面资源全部重拉。
考虑改成「连续失败 2 次以上才轮换」，但这会改变换指纹的频率，需要有数据再动。

### 5.5 死代码

`real_mouse_coordinates.calibrate_slider_center()` 在 rebase 后已无调用方（上游改用被动窗口几何映射 `build_geometry_mapper`）。
如果哪天怀疑坐标精度问题，它是现成的主动校准实现，可以捡回来用。
